# 管理中心 Redesign — IA / Flow 提案 v1

日期：2026-07-09 · 范围：完整管理中心（总览、审批、成员、交易、抽成、成员详情/冻结/拒绝原因）
性质：自由重构提案，可推翻 HANDOFF 中群主面板 V2.1 的已确认决策。确认方向后再做原型（新文件夹内，不动现有 index.html）。

---

## TL;DR

现在的管理中心把「要做的事」（审批）埋在「查东西的地方」（成员名单）里，而审批最需要的数字（可分配余额 240）根本不在总览上。推荐推翻 3-tab 结构，改成**单页纵览 + 二级任务页**：首页一屏看清额度池、佣金、待办、成员快照；审批独立成全屏队列页，从待办一步直达。

---

## 一、现状诊断（6 个问题）

1. **关键数字缺位。** 审批时唯一决定「能不能批」的数字是可分配余额（240），它只出现在审批卡的报错里。总览 hero 给的 1,855 反而没有任何行动意义——而且 1,855 和 240 的口径关系不明（总池？已分出？含冻结？）。
2. **同一件事提醒三次，路径却最深。** tab 红点 + 「待审批(3)」pill + 总览黄条，三处都在喊同一个「3」；但真正去处理要跳两层（切 tab → 切 segmented）。通知冗余、动线反而长。
3. **任务流和名单混在一个 tab。** 「待审批」是要做的事，「全部成员」是查东西——两种心智模型硬塞进一个 segmented。结果是 segmented + 搜索 + 状态 chips 三层控制器堆叠，找个人要先理解过滤逻辑。
4. **额度不足按卡逐张报错，且是死胡同。** 池子不够是全局问题，却在刘姐、周先生每张卡上重复黄条；「通过」禁用后没有任何出路。回收额度这个动作明明存在（吴先生 +80），却藏在交易记录里，没接到最需要它的审批场景。
5. **两种资金语义挤一张金卡。** 佣金是收入，额度是运营资源，性质完全不同；混在同一张 hero 里导致谁都不是重点。
6. **设置 tab 只有一行。** 导航成本大于内容价值。另外「0.0008% · 按玩家盈利」疑似口径错误——按盈利抽 0.0008% 约等于零，大概率是 0.08% 或 8‰ 写错，需 client 澄清。

## 二、三个结构方向

### 方向 A · 任务收件箱型
2 tab（今日 / 成员），设置收进右上角齿轮。「今日」首屏 = 池状态条 + 可直接 inline 处理的审批队列 + 佣金摘要。审批零跳转，适合高频审批的群主。代价：首页承担操作，误触风险高，卡片多时首页变长。

### 方向 B · 资金台账型
保留 3 tab 但按对象重组：总览 = 额度池卡 + 佣金卡两张独立卡；成员 tab 变纯名单（去掉待审批 segmented）；审批独立成全屏队列，从待办条直达、不经过成员 tab。改动最温和，保留现有导航习惯。

### 方向 C · 单页纵览型（推荐）
去掉 tab。首页像银行 App 一屏滚动：额度池卡 → 佣金卡 → 待办入口 → 成员快照 → 最近交易 → 设置行；所有深内容 push 进二级页。理由：管理中心功能总量就这么多，3 个 tab 是过度设计；单页让层级最浅、导航概念最少，也最容易日后加块（如公告、报表）而不用重排导航。

| 维度 | A 收件箱 | B 台账 | C 单页纵览 |
|---|---|---|---|
| 导航概念数 | 2 tab + 齿轮 | 3 tab + 内层 | 0 tab，纯 push |
| 审批路径 | 0 跳（inline） | 1 跳 | 1 跳 |
| 误操作风险 | 较高 | 低 | 低 |
| 扩展性 | 中 | 中 | 高 |
| 相对现状改动 | 大 | 小 | 中 |

推荐 **C 为骨架，吸收 A 的「审批一步直达」**。若 client 对去 tab 有心理障碍，B 是安全退路。

## 三、推荐方案（C）屏幕清单

### 1. 管理中心首页（单页滚动）
- **额度池卡**（首要位置）：主数字 = **可分配 240**；副行 = 已分配 1,615 · 今日变动 −270；次按钮「回收额度」。审批能力一眼可判。
- **佣金卡**：今日 +68 / 累计 1,240 / 比例（口径文案修正后展示）；点入佣金明细。
- **待办卡**：「3 笔额度申请 · 最早 09:48 ›」→ 直达审批队列。这是全 App 唯一的待办数字来源（入口 badge 沿用同一总数）。
- **成员行**：「成员 8 · 活跃 4 · 冻结 1 ›」→ 成员列表。
- **最近交易**：3 条 + 查看全部。
- **设置行**：抽成设置等 › 。

### 2. 审批队列页（新，独立全屏）
- 顶部**常驻池状态条**：「可分配 240」，随批准实时递减——全局问题只说一次，不再每卡重复。
- 卡片排序：**可批在前，不足在后**（王哥 200 排第一）。
- 额度不足不再是死胡同，卡上给两条出路：
  - 「回收后可批」：列出可回收建议（如：回收 吴先生 未用 80 + 李姐 未用 300 → 够批 600）；
  - 「部分批准」（业务上是否允许待 client 确认，见开放问题 2）。
- 批/拒二次确认保留；完成后原位变状态 ✓（这条旧决策值得留）。拒绝原因可选、成员可见。
- 入群申请与额度申请仍分两节，共用同套交互。

### 3. 成员列表页
- 只留搜索 + 状态 chips（全部/活跃/不活跃/已冻结），**删掉 segmented**。
- 行信息升级：姓名 · 最后投注 · **剩余额度** · 状态 chip——剩余额度是群主看名单的核心诉求，现在完全没有。
- 点行 → 成员详情。

### 4. 成员详情页
- 额度区：剩余 / 累计分配 / 累计回收；动作：分配额度、回收额度、冻结。
- 该成员的申请与审批历史。
- 冻结走居中二次确认。

### 5. 交易记录页
- 类型筛选：分配 / 回收 / 佣金入账（佣金流水目前没地方看，补上）。

### 6. 抽成设置页
- 结构不变，修口径与文案；改动需二次确认 + 生效时间说明。

### 流程图

```
频道 header「管理」+ badge(3)

        ▼
  管理中心首页 ──┬─ 待办卡 ──▶ 审批队列 ──▶ 批/拒确认 ──▶ 原位状态
                ├─ 成员行 ──▶ 成员列表 ──▶ 成员详情 ──▶ 分配/回收/冻结

                └─ 设置行 ──▶ 抽成设置
```

## 四、需 client 确认的开放问题

1. **1,855 与 240 的口径**：1,855 是总池还是累计分出？可分配 240 是否已扣冻结成员占用？
2. **额度不足时允许部分批准吗**？还是只能「先回收再批」或拒绝？
3. **0.0008% 单位**：疑似应为 0.08% 或 8‰；按玩家盈利的结算周期是什么？
4. **回收额度规则**：只能回收未使用部分？需成员同意还是群主单方面？
5. **待办范围**：除额度/入群申请，提款审批是否也进同一队列（钱包侧有「等待群主确认」）？
